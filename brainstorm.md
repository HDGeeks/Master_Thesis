# Brainstorm: Improvement Ideas for BTW2025-122

Laptop-feasible ideas only, easy to medium difficulty, no hard/heavy options. To be vetted later for feasibility and difficulty before picking a thesis focus.

Examples below reuse the paper's own Figure 1 document where possible: title "Harnessing the power of two crossmatches", ground truth subjects = computer hardware, computer networks, computer systems, information retrieval, information technology, internet, theoretical computer science.

## Easy (code/prompt changes, no new model needed)

1. Post-hoc answer cleanup: strip quotes, punctuation, extra whitespace, then fuzzy match (edit distance or token overlap) so near-misses like "computer vision" still hit "computer imaging and vision"
   - Why better: the paper's matching was exact-string only after lowercase and trim. Their own examples of hallucination, the quoted `"'software engineering'"` and `"computer vision"` vs `"computer imaging and vision"`, would both be caught by this. Attacks a real slice of the 25-33% hallucination rate without touching the model at all.
   - Example: LLM answers `"'software engineering'"` (with inner quotes). Old pipeline: no match, counted as hallucination. New pipeline: strip quotes first, get `software engineering`, which is a valid vocabulary term, counted as success or misclassified depending on ground truth instead of being thrown away.

2. Ask for top-3 topics instead of 1, then score against the full multi-label ground truth (docs already average 4.5 labels, so top-1 was always going to look worse than it deserves)
   - Why better: the paper forces the model into a 1-label answer against documents that carry 4.5 labels on average. That mismatch alone caps the ceiling of the success rate. Scoring top-3 against the full label set gives credit for correct-but-not-first answers instead of penalizing them as misclassified.
   - Example: for the crossmatches paper, suppose the LLM's top-3 answers are "artificial intelligence", "internet", "information technology". Old metric (top-1 only, "artificial intelligence"): misclassified. New metric (top-3 against all 7 ground truth labels): 2 of 3 answers correct, a very different picture of how well the model actually did.

3. Recompute evaluation as multi-label precision/recall/F1 instead of the current success/misclassified/hallucination split, using the outputs already produced
   - Why better: the paper's own limitation list flags that "misclassified" penalizes plausible answers. A document can have several correct topics, so an answer that isn't the one label shown still might be right. P/R/F1 against the full subject list reflects this instead of a binary right/wrong verdict.
   - Example: for the crossmatches paper, the LLM answers "computer networks" (one of the 7 correct labels). Old metric: counted simply as one success. New metric: precision = 1/1 (the one label it gave is correct) but recall = 1/7 (it only found one of seven true labels), showing the model is accurate but far from complete, information the old binary metric hides entirely.

4. Few-shot prompting: add 2-3 example title-to-topic mappings inside the existing 3-turn prompt
   - Why better: the paper is strictly zero-shot, no examples of the exact wording expected. Concrete input-output examples could anchor the model to the controlled vocabulary's exact strings, directly targeting cases where it defaulted to close-but-wrong wording.
   - Example: add to the prompt "Title: 'Convolutional networks for image segmentation' -> Topic: computer imaging and vision" before asking about the target title. Seeing the exact string "computer imaging and vision" used correctly makes the model less likely to shorten it to "computer vision" on the next document.

5. Chain-of-thought prompting: ask the model to reason first, then extract the final label from the response
   - Why better: the paper asks for a single word with zero reasoning space. The most common hallucination was the model answering the parent category "computer science" instead of a specific topic, arguably a sign of the model being unsure and falling back to the broad label. A reasoning step gives it room to work through the distinction before committing.
   - Example: prompt asks "Think step by step, then end with 'Answer: <topic>'". For the crossmatches paper the model might reason "this is about a matching algorithm between donors and patients, which is a theoretical algorithms problem... Answer: theoretical computer science" instead of jumping straight to the vaguer "computer science".

## Medium (small model or lightweight ML, still laptop-runnable)

6. Embedding-based retrieval baseline: embed the 19 topic labels and the title/abstract with a small sentence-transformer (e.g. MiniLM), pick the topic by cosine similarity, no generation at all
   - Why better: hallucination exists in the paper because the model has to generate and reproduce an exact string. Similarity search has no generation step, so an invalid label is structurally impossible. Also far cheaper to run than a full LLM call per document.
   - Example: embed the title "Harnessing the power of two crossmatches" and all 19 topic strings with MiniLM, take the highest cosine similarity, e.g. "theoretical computer science". That string is always one of the 19 by construction, so the paper's most common failure case, answering "computer science" or a quoted/misworded label, cannot happen at all.
   - Caveat (verdict: weak as a standalone replacement): titles are short and often share no vocabulary with the correct topic label, e.g. "Harnessing the power of two crossmatches" has nothing lexically in common with "theoretical computer science". An LLM can bridge that gap with background knowledge (kidney exchange is a matching/graph algorithm problem); pure embedding similarity cannot make that inferential leap, only match meaning-overlap. So this removes hallucination but likely caps accuracy lower on titles specifically. Keep as a cheap no-hallucination reference point and as the retrieval half of idea 10, not as a proposed replacement on its own.

7. Classical ML baseline: TF-IDF plus logistic regression or SVM trained on this labeled dataset, to show where zero-shot LLM actually stands against a cheap supervised method
   - Why better: the paper never compares against a supervised baseline, so there is no way to know if ~50% success is actually good. This gives a reference point for what the "zero-shot" framing is actually buying versus a simple trained model.
   - Example: train logistic regression on TF-IDF vectors of 2000 titles from the same D3 subset, test on the remaining 500. If it reaches, say, 55% top-1 accuracy in under a minute of training with zero hallucinations, that is a strong finding on its own: the LLM's 3.5 hour run may not be worth its 25-33% hallucination cost compared to a method this cheap.
   - Mechanism in more detail: split the 2500-doc subset train/test (e.g. 80/20), vectorize titles with TF-IDF, and train as genuine multi-label classification (one-vs-rest logistic regression, one binary classifier per topic, 19 total) since docs average 4.5 ground-truth topics, same mismatch the paper has. Evaluate with the same multi-label precision/recall/F1 as idea 3 so the numbers are directly comparable. Training time on a laptop is seconds.
   - What question it actually answers: not "does classical ML beat the LLM," but "is the ~50% ceiling caused by the task being genuinely hard, or by the zero-shot LLM specifically being bad at it." If TF-IDF also caps near 50%, the dataset itself is the bottleneck. If it clears 50% by a wide margin, that says the zero-shot approach is leaving real performance on the table, a stronger and more citable result.
   - Caveat (why this isn't apples-to-apples): needs labeled training data, which breaks the paper's "zero-shot, no examples" framing. It answers a narrower question, how good a trivial supervised baseline is on this exact dataset, and should be reported as context, not as a competitor doing the same task.
   - Deeper caveat worth reporting as its own finding: the ground truth labels come from the CSO classifier, which itself has a syntactic (keyword-matching) module (paper's own limitation: ground truth is automatic, not human-annotated). TF-IDF is also purely lexical. So a strong TF-IDF score may partly just mean a lexical method can reproduce another lexical method's output, not that the topic is recoverable from real meaning. That gap itself, how much of the CSO labels are surface-wording-recoverable versus not, is a genuinely interesting methodological point about the dataset.

8. Compare a couple of small quantized open models (Phi-3-mini, Gemma 2B, Qwen 1.5B) run locally via Ollama/llama.cpp, same prompt and eval pipeline as the paper
   - Why better: the paper tested exactly one model (Llama 3 8B) with no ablation, listed by the authors themselves as a limitation. Running a couple of alternatives on the same pipeline shows whether the hallucination rate is a property of this specific model or a systemic issue with the zero-shot approach.
   - Example: run the identical 3-turn prompt for the crossmatches title through Llama-3-8B and Phi-3-mini. If Llama answers "computer science" (hallucination) but Phi-3-mini answers "theoretical computer science" (success) on the same input, that is direct evidence the hallucination is a model-specific quirk, not a property of the zero-shot method itself.

9. Constrained decoding: force the model to only output a valid vocabulary term (grammar-constrained generation, e.g. via llama.cpp grammars or the Outlines library)
   - Why better: most of the paper's hallucinations are formatting or recall problems (wrong wording, quotes, parent category), not the model misunderstanding the document. Constrained decoding removes invalid strings by construction at generation time, a more direct fix than cleaning up the output afterward like idea 1.
   - Example: set a grammar that only allows the 19 exact topic strings as valid completions. Asked about the crossmatches title, the model physically cannot output "computer science" (not one of the 19 subordinate topics), so it is forced toward the closest valid option, e.g. "theoretical computer science" or "information retrieval", both of which are actually in the ground truth.
   - Mechanism in more detail: grammar-constrained decoding masks out, at every generation step, any next-token that would lead off the path of one of the 19 valid strings. The model still uses its own learned preferences to choose among what remains valid, it is not picking randomly, it just cannot wander outside the 19-item set. A grammar is literally an alternation of the 19 exact strings (`root ::= "artificial intelligence" | "computer aided design" | ... | "bioinformatics"`).
   - Implementation path: llama.cpp supports this natively via GBNF grammars and can load the exact same model file the paper used (Meta-Llama-3-8B-Instruct.Q4_0.gguf), since GPT4All is itself built on llama.cpp. Low-friction swap, not a new model, just a different runner. Alternative: Hugging Face transformers with a custom LogitsProcessor, or libraries like Outlines/lm-format-enforcer. Runs on CPU or a laptop GPU, no cluster needed.
   - Side effect: since the output is guaranteed to be one of the 19 strings exactly, idea 1's post-hoc cleanup becomes unnecessary for this pipeline, the matching step collapses to plain equality. A synergy, not a redundancy.
   - What gets measured, the real research question: rerun the same 3-turn prompt on a document sample with the grammar applied on the final query, compare the resulting success/misclassified/hallucination split against the paper's own numbers (50/25/25 titles, 50/17/33 abstracts). Hallucination drops to 0% by construction, so every former hallucination is forced into success or misclassified. Which way it breaks is the actual finding: if success rises, the model "knew" the answer but was escaping into free text under uncertainty; if most land in misclassified instead, the model genuinely didn't know and forcing a choice just relabels the same confusion (still a real usability win, since every output becomes parseable, even without an accuracy gain). Either outcome is a legitimate, citable finding, not a foregone conclusion.
   - Feasibility scope: no need to match the paper's full 2500 docs x 5 runs x 2 representations. A sample of 300-500 documents, run once or twice, is enough given the paper's own runs already showed very low run-to-run variance. On a quantized 8B model via llama.cpp on a modern laptop, that is on the order of tens of minutes to a couple hours.
   - Caveats: fixes hallucination only, not misclassification, so the paper's headline success rate might not move much even though the pipeline gets objectively more usable. Should be reported together with idea 3's multi-label P/R/F1, since a constrained answer could be a correct-but-different label than the one shown in a binary ground truth check. Grammar size grows with vocabulary size, a natural link to idea 10's scalability question as future work rather than something this thesis needs to solve too.

10. Hybrid retrieval plus generation: pre-filter the 19 topics down to the most relevant few using embedding similarity, then let the LLM pick from that shortlist instead of the full list
    - Why better: the paper always shows the model the full 19-item list regardless of the document, and the authors explicitly flag vocabulary scalability (19 to 100 to 1000 topics) as untested future work. A shortlist tests whether a smaller, more relevant candidate set reduces confusion, and is a first step toward the scalability question the paper raises but never runs.
    - Example: embedding similarity narrows the 19 topics down to the 5 closest to the crossmatches title, e.g. theoretical computer science, information retrieval, computer networks, data mining, computer systems, and the LLM is only asked to pick among those 5 instead of all 19, cutting the chance it wanders off to an unrelated or invalid label.

All ten can run on a laptop CPU or a modest GPU with quantized/small models, no cluster or fine-tuning needed.

## Notes from paper reread

- The evaluation code already supports comma-separated multi-topic answers (built for future extensibility), only prompted for 1 topic. Relevant to idea 2.
- Authors' own future work already names: self-correction loop for hallucinations, scalability testing across more topics, further STTCL preprocessing. A thesis should go further than these, not just execute their stated plan.
